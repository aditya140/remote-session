# Gateway routing contract

The gateway exposes authenticated WebSocket upgrades at `/v1/connect/client` and `/v1/connect/host`. Deploy these behind a trusted TLS edge. Client upgrades use the dedicated remote user JWT; host upgrades use the proof-of-possession machine token. Both use the REST identity service and durable PostgreSQL access state. Affinity headers have no authority and are ignored.

Send protocol 1.0 `hello`, negotiating `routing-v1` and, for clients, `machine-pages-v1`. `auth-refresh-v1` enables in-place credential renewal. The server sends `welcome` and `connection.ready` with the assigned connection ID and, for hosts, the durable host generation. `activated:false` explicitly means native mutations are unavailable until task 017 supplies the sessiond activation acknowledgement. Starts, inputs, control leases, termination, and approval decisions currently return `unsupported_capability`/`not_sent`.

The edge waits for an acknowledged owner subscription before normal remote routing; a three-second deadline permits degraded local admission during an outage, and unavailable cross-node reads fail explicitly. Clients receive an initial `machine.page` epoch, page index, and total. Pages contain at most 64 machines and approximately 512 KiB of machine data; an empty inventory still has one page. Replace inventory only after all pages in an epoch arrive, then apply `machine.updated`. The server reconciles durable metadata and presence every two seconds against each client’s last delivered digest. Per-client cutover locks and ordered read revisions preserve a rename that occurs during an initial snapshot. Inventory pages/deltas share one FIFO priority lane; a slow writer holds only its own cutover. A revoked machine causes a fresh epoch. Large inventories use WSS pages; the REST list rejects responses exceeding 512 KiB. Session projections reject lists exceeding 1,024 sessions or 512 KiB until SDK session pagination is added in task 023.

Hosts publish their own inventory and session metadata. PostgreSQL verifies the machine/owner/key/generation while locking projection writes against host replacement. Initial prompts are removed from durable session metadata. Session counts include accepted, launching, running, and idle sessions. Clients can browse durable session metadata while the host is offline. Live filesystem, attach, start-lookup, and approval-list reads route to the connected host. Every target follows the session-to-machine-to-owner chain. Only attached, authenticated clients receive a session's output.

The server renews signed Redis routing hints every two seconds. Hints expire after 25 seconds and are accepted for at most ten seconds after signing. Presence appears within five seconds in the verified two-node fixture; unclean disconnect is reflected within thirty seconds. PostgreSQL generations supersede older sockets and stale hints. The full u64 generation range uses PostgreSQL numeric and decimal wire strings. A generation cannot wrap. This reservation is separate from native activation in task 017.

## Redis failure and delivery

Same-node dispatch bypasses Redis and checks live PostgreSQL authority for each operation. The connector/process owner remains independent of the gateway. Cross-node dispatch uses sharded pub/sub with per-node replies and per-user output fanout. Redis stores no durable output, leases, approvals, or identity authority. A domain-separated HMAC authenticates internal packets and hints; destination, age, and generation checks reject replayed or stale routes. Request packet identities are retained for the full fifteen-second timestamp acceptance window. User bearer credentials are intercepted at the edge and never forwarded to Redis or hosts.

Pub/sub is at most once. Discovery reconnection rebuilds subscriptions and hints; it never resends an operation. A lost subscriber, queue overflow, or failed routed delivery causes explicit uncertainty/resync or connection closure for affected remote observers. Source-side publish loss is retained as a bounded resync obligation and announced after Redis reconnects; it cannot silently strand observers on healthy subscriber nodes. Retired subscriber/publisher callbacks are fenced from replacement connections. Same-node observers continue directly while PostgreSQL remains authoritative. Clients must reconnect and attach/replay from their last sequence. A successful socket write is not a native application acknowledgement. In-place token refresh must retain the same user, or the same machine/owner/key; expired/revoked identities close their sockets.

Per-node limits include 4,096 sockets, 128 subscribed owners, 32 clients per owner, 128 session subscriptions and pending client requests, and 4,096 pending requests globally. Pending replies expire after ten seconds. Four concurrent initial inventory enumerations are permitted. Per-owner inventory is capped at 1,024 machines/8 MiB. Delivered digests are shared where possible and capped at 1,024 entries per client; they store hashes, not prior metadata copies. Common transport queues retain their per-socket message/byte limits, plus shared outgoing budgets of 8 MiB control, 16 MiB event, and 32 MiB bulk, and 16 MiB incoming. Redis has separate control/event/bulk connections, 32 concurrent publishes per lane, and 2/4/16 MiB lane budgets; the subscriber inbox is bounded to 512 packets/16 MiB. A slow observer closes independently. Capacity qualification and aggregate measurements remain task 028.

## Configuration and verification

Add these flags to the identity-enabled `serve` command:

```sh
--redis-url-file /run/secrets/redis_url \
--routing-key-file /run/secrets/routing_hmac_key \
--redis-ca-file /run/secrets/redis_ca.pem
```

The routing key is a separate random 32-byte base64 value shared by gateway replicas. URL/key files must be bounded regular files without world access. Use `rediss://` with ACL credentials and verified CA roots in deployment. Plain Redis is accepted only for localhost/loopback development fixtures. Redis uses RESP3; insecure TLS URI fragments are rejected. Diagnostics redact URLs, keys, and bearer credentials.

The ignored gateway integration test requires disposable PostgreSQL 17, Redis 8, and the freshly built gateway binary. It creates a generated database, starts **two actual gateway processes**, serves synthetic public JWKS over verified HTTPS, and connects through verified WSS. It exercises ownership and token-family denials, push inventory/counts/presence, cross-node request/reply/output, multi-page terminal checkpoints plus final head, late duplicate responses, maximum-size JSON, slow-observer isolation, credential refresh, replacement/fencing, Redis pub/sub loss and a full finite Redis pause, same-node reads during that pause, recovery, revocation, u64 exhaustion, and SIGTERM cleanup. Its host is an explicit protocol fixture. Separate actual native connector/sessiond, managed Codex and four-gateway deployment proofs are recorded in [MVP evidence](../validation/mvp-evidence.md); real tenant and representative scale remain external release gates.

An attach reply may be one replay/head response, or a contiguous `session.snapshot` epoch followed by a correlated `session.head`. Every page has the same epoch/cursor/dimensions/format/count and ordered indexes. The final head must be at least the capture cursor. Pending correlation remains bounded by the original ten-second deadline; it is not renewed by pages. Snapshot payloads use `vt100_state_v1`, at most 32 pages of 256 KiB, with an eight-MiB complete-state limit. The gateway validates framing/correlation and does not parse native terminal state. Missing/mixed/incomplete epochs require resync.
