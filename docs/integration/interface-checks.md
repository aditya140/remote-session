# Interface checks and compatibility baselines

The command reference comes from the executable Clap definitions. The test parses
shell command examples in `README.md` and Markdown files under `docs`. It handles
shell fences, quoted arguments, and continued lines. It replaces documented ID
placeholders with synthetic typed IDs. It does not expand shell variables or run
an example. Descriptions of proposed `qgenie` integration are outside this check.

Run these commands after a CLI change:

```sh
QGR_UPDATE_CLI_DOCS=1 cargo test -p qgenie-remote --bin qgenie-remote cli_contract
cargo test -p qgenie-remote --bin qgenie-remote cli_contract
python3 tools/check_compatibility.py
```

Review both generated files: `docs/integration/cli-reference.md` and
`conformance/cli/current.json`. The first contains help text. The second contains
command and argument contracts. The check detects stale generated files and
examples that the current parser rejects. It never calls command dispatch.

## Baseline status

The repository advertised no release tags when this work was prepared. The first
baseline is therefore **preview**, at revision
`9ea149b8dd3b113d5d73992e9b9b27c8affb917b`. Its CLI contract was generated by that
revision's actual Clap definitions in an isolated checkout. Its wire schemas
come from that same revision. This establishes a preview comparison. It does not
establish the PRD's N-2 released-client qualification.

`conformance/compatibility/baselines.json` names each immutable revision and file
digest. The checker compares active preview baselines and the latest three
released baselines. Keep entries in release order. The three released baselines
represent the current release and its two predecessors. Before three releases
exist, retain every published release.

The structural check rejects removed commands or fields, changed existing CLI
arguments, new required input, changed required output, incompatible types and
bounds, and removed enum members. It permits new optional fields and new tagged
variants. Such additions still require behavioral capability tests. A reviewed
enum addition must be named explicitly in the manifest. The new ambiguous-name
error is used only by negotiated session metadata operations.

Current schema freshness and network conformance fixtures remain required.
Behavioral tests check old-peer capability refusal, legacy prompt behavior,
missing historical metadata, exact receipts, and observation recovery. A schema
comparison alone cannot establish authentication, control, or lifecycle behavior.
Native SQLite and gateway PostgreSQL upgrade rules are separate from network
client compatibility.

## Release procedure

1. Select the exact release candidate revision. Run all required CI and the
   applicable external release gates.
2. Create a new baseline directory named for the release. Generate its CLI
   contract from that revision. Copy its public, REST, and recording schemas.
3. Add its version, immutable revision, status `released`, and file digests to
   the manifest. Keep the existing release entries and fixtures unchanged.
4. Compare the candidate with the previous two published client contracts.
   Run the behavioral compatibility tests. Record any unrun platform checks.
5. Review every capability addition and result change. Add focused old-peer
   behavior tests. Do not approve a breaking change by replacing old fixtures.
6. Run the interface checks without update mode. Publish only after the
   supported release window passes.

Until released baselines exist, the N-2 release gate remains open. Do not relabel
preview evidence as a released-client result.

## CI cost

Code changes run these checks in the existing workspace suite. Documentation
changes run a focused CLI test and the static contract checks. They do not build
or start the deployment. The generated help test reads files and parses arguments;
it does not enroll a host, submit a prompt, or start a session.

Pull requests run on `pull_request`. Push checks run on `main` and release tags.
This removes the duplicate full run for every push to an open feature PR. The
required CI gate distinguishes intentional skips from failures. Manual runs can
still request all checks.

On this Linux workspace, the warm CLI test took 0.09 seconds inside the test
runner. It parsed 45 examples. The 14 Python tool tests took 0.40 seconds.
The new old-peer prompt test took 0.13 seconds. These are local measurements.
Cold hosted compilation and cache download time are not included.
